# Proposal: Realtime Tenant Isolation

## Intent
The multi-tenancy foundation isolates HTTP and Eloquent data paths: every tenant-scoped query is filtered by `school_id` via `TenantScope`, and `ResolveTenant` binds the current `School` for the request lifecycle. But the real-time path has NO equivalent isolation. Laravel Reverb runs as a separate ReactPHP process with zero visibility into the HTTP kernel, `TenantScope`, or `TenantContext`. Broadcast authorization lives entirely in `Broadcast::channel()` closures in `routes/channels.php`, and today the only channel is the framework default (`App.Models.User.{id}`) — there is NO tenant-scoped channel convention at all. This change establishes the real-time tenant-isolation foundation: a documented, helper-backed, test-guarded convention for how every future module names and authorizes school-scoped broadcast channels, plus a tenant-aware `api` rate limiter so one noisy tenant cannot starve the shared connection/auth budget of others.

**Why now**: this mirrors the exact "cheapest moment" rationale of `multi-tenancy-foundation`. No module broadcasts anything yet — `routes/channels.php` holds a single framework-default channel and zero business channels. Establishing the school-scoped channel naming + authorization pattern while there is nothing to retrofit is nearly free. Once Grades, Notifications, Schedule, etc. each start declaring their own channels, seven modules will independently reinvent (or forget) tenant checks in closures that the global scope cannot protect — and a single forgotten `$user->school_id` comparison silently leaks another school's live data to a subscriber. Getting the pattern, the helper, and the guardrail test in place before the first real channel exists is the moment with the lowest cost and the highest leverage.

**What success looks like**: a developer adding a real-time feature in any module has ONE documented way to name a channel (`private-school.{schoolId}.{resource}.{id}`) and ONE helper to authorize it (compare `$user->school_id` to the channel's embedded `schoolId`), so a subscriber authenticated for school 1 can never receive school 2's broadcasts; the `api` rate limiter partitions its budget per school so a burst from one tenant does not throttle another; and the isolation discipline is enforced by an architecture-level guardrail test rather than by reviewer memory. Reverb's Redis-backed horizontal scaling stays wired-but-off, with a documented, evidence-based trigger for when to flip it on.

## Scope
### In Scope
- **Tenant-scoped channel naming + authorization convention** — a documented pattern plus a small tenancy-core helper (e.g. `App\Tenancy\Broadcasting`) that (a) builds a school-scoped channel name from `(schoolId, resource, id)` and (b) provides the standard authorization predicate (reject `$user->school_id === null` outright, then validate `$schoolId` is a well-formed positive integer before comparing `(int) $user->school_id === (int) $schoolId`) so the 7 future modules share one implementation instead of copy-pasting closure bodies.
- **Tenant-aware `api` rate limiter** — extend the existing `RateLimiter::for('api', ...)` closure in `app/Providers/AppServiceProvider.php` to key by the resolved `school_id` (via `app(TenantContext::class)->current()?->id`) in ADDITION to the current user/IP key, so per-tenant buckets are independent.
- **Reverb scaling decision + documentation** — record the decision to keep `REVERB_SCALING_ENABLED=false` for now, document that the Redis infra is already provisioned and "ready to enable", and define the concrete signal that should trigger flipping it later.
- **Guardrail test approach for channel-naming discipline** — decide what is genuinely testable at foundation stage (helper behavior, authorization predicate, tenant-aware limiter partitioning, an exemption-aware channel-registry discipline test) versus what must wait for the first real channel, following the spirit of `tests/Feature/SecurityBaselineTest.php`.

### Out of Scope (future separate SDD changes)
- Any actual per-module real-time feature (Grades live updates, Notifications push, Schedule live changes, attendance, presence, chat, etc.). This proposal builds the reusable pattern, not the features.
- **Enabling Reverb Redis horizontal scaling** (`REVERB_SCALING_ENABLED=true`) — deferred until real concurrent-connection load exists; infra stays wired-but-off.
- **Frontend / Laravel Echo client wiring** (Vue/Inertia/Pinia side) — this proposal is backend authorization/isolation only. Client subscription code arrives with the first real feature.
- Making the **`login`** rate limiter tenant-aware — login happens pre-tenant-auth and is already keyed by `email|ip` (`AppServiceProvider` boot, driving `routes/web.php` login route); adding `school_id` there is neither needed nor correct for v1.
- Presence-channel member-list privacy semantics, per-channel authorization roles/permissions (Spatie gates on channels), and broadcast payload field-level redaction — deferred to the first feature that needs them.
- Per-tenant Reverb connection quotas / per-school connection caps (a scaling-era concern, not a foundation concern).

## Capabilities
### New Capabilities
- `realtime-tenant-isolation`: school-scoped broadcast channel naming + authorization convention, tenancy-core broadcasting helper, and the channel-discipline guardrail test.
### Modified Capabilities
- `security-baseline`: the `api` rate limiter becomes tenant-aware (keyed by `school_id` in addition to user/IP), partitioning the shared request budget per tenant.

## Approach
Exploration recommendation (already confirmed, not re-derived): embed the tenant id in the channel name and validate it in the authorization closure against the authenticated user's own `school_id`, reusing the existing `/broadcasting/auth` → `ResolveTenant` path rather than adding middleware or relying on request-scoped `TenantContext` inside closures.

Mechanics:
1. **Channel naming convention.** School-scoped private channels follow `private-school.{schoolId}.{resource}.{id}` (Laravel's `private-` prefix is implicit in `Broadcast::channel('school.{schoolId}...')`; the wire name carries it). `{schoolId}` is the numeric `schools.id`, `{resource}` is a stable module noun (e.g. `grades`, `notifications`, `schedule`), `{id}` is the resource key. The tenant segment is ALWAYS the first segment after the type prefix so it is greppable and machine-checkable.
2. **Authorization predicate — validate against `$user->school_id`, NOT `TenantContext`.** The closure first rejects `$user->school_id === null` outright (no cast), then validates `$schoolId` is a well-formed positive integer before comparing `(int) $user->school_id === (int) $schoolId`; a naive cast-only comparison is unsafe because PHP casts both `null` and non-numeric strings to `0`, which would let a landlord user coerce-match a malformed channel segment. This is deliberate and load-bearing: `TenantContext` is request-scoped and IS populated on the synchronous `/broadcasting/auth` HTTP call (which runs through `ResolveTenant` via the `web` group), but it is NOT bound for broadcasts emitted from queued jobs or console commands. Authorizing against the user's persisted `school_id` is robust in every context; authorizing against `TenantContext::current()` would be a latent bug the moment a broadcast is queued. The helper encodes this so modules cannot get it wrong.
3. **Tenancy-core broadcasting helper.** A small `App\Tenancy\Broadcasting` unit (final placement — class vs. helper functions — is a design-phase call) exposing at minimum: a name builder `schoolChannel(int $schoolId, string $resource, int|string $id): string` and the authorization predicate `authorizeSchool($user, $schoolId): bool`. It lives in the tenancy core (`App\Tenancy`, beside `School`/`TenantContext`/`TenantScope` per the multi-tenancy design) because channel isolation is cross-cutting tenancy infrastructure consumed by every business module, never owned by one.
4. **Tenant-aware `api` limiter.** In `AppServiceProvider::boot()`, extend the existing `api` limiter key from `user-or-IP` to include the resolved tenant: `by($schoolId ? "school:{$schoolId}|{$key}" : $key)` where `$schoolId = app(TenantContext::class)->current()?->id`. `TenantContext` is already registered as an app-`scoped` singleton in `register()`, so the closure body (which runs per-request, not at boot) resolves the correct tenant. Landlord/unresolved requests (`school_id` null) fall back to the existing user/IP key — no behavior change for the landlord path. The `login` limiter is untouched.
5. **Guardrail test — what is testable now.** Following `SecurityBaselineTest` style (Pest, `beforeEach` route/channel registration):
   - **Helper behavior**: `schoolChannel(...)` produces the exact `school.{id}.{resource}.{id}` shape; `authorizeSchool()` returns `true` only when the user's `school_id` matches the embedded id and `false` otherwise (including string/int coercion and null `school_id`).
   - **Tenant-aware limiter partitioning**: two requests bound to different tenants consume independent `api` buckets; a request that exhausts school 1's budget does not throttle school 2 (behavioral test, mirroring the existing `api limiter consumes exactly one quota unit` test).
   - **Channel-registry discipline (exemption-aware)**: an architecture test that enumerates registered broadcast channels and asserts every channel EXCEPT an explicit allow-list (the framework default `App.Models.User.{id}`, which is per-user not per-tenant) begins with the `school.{schoolId}` tenant segment. Today it passes trivially (only the exempt default exists); its VALUE is future — it fails the build the day a module registers `grades.{id}` without the tenant prefix.
   - **What must wait**: end-to-end subscribe/receive isolation (subscriber for school 1 cannot receive a school 2 broadcast over a live connection) needs a real channel + a real broadcast event, so it is deferred to the first feature. The foundation asserts the discipline that makes that impossible to get wrong, not the runtime delivery.

### Key decisions (resolved, with rationale)

**Decision 1 — Isolation lives in channel authorization, not middleware.**
Reverb never runs the HTTP kernel, so no middleware it "sees" can enforce anything. `/broadcasting/auth` already runs through `ResolveTenant` (Laravel registers the broadcasting-auth route in the `web` group automatically; `bootstrap/app.php` appends `ResolveTenant` to `web`), so no middleware change is needed or possible for Reverb itself. All enforcement is in the closure. Confirmed by exploration; no gap.

**Decision 2 — Authorize against `$user->school_id`, not `TenantContext`.**
`TenantContext` is request-scoped; it is correct on the synchronous auth call but absent for queued-job broadcasts. Comparing the channel's embedded `schoolId` to the user's persisted `school_id` is context-independent and cannot silently break when a broadcast is later moved to a queue. The helper enforces this so it is not a per-module choice.

**Decision 3 — Keep `REVERB_SCALING_ENABLED=false`; document the flip trigger.**
Redis is fully provisioned (Sail service, `config/database.php` redis connection, `config/reverb.php` scaling section reads `REDIS_*`). Enabling scaling needs no new infra. But there is zero concurrent-connection load today, and enabling it adds a Redis pub/sub hop and a shared-state failure surface for no current benefit. Decision: stay off; document that the trigger to enable is real evidence of multi-instance Reverb need (horizontal Reverb scaling / >1 Reverb process, or measured connection saturation on a single process), verified against the `REDIS_*` DB/instance-collision risk the exploration flagged (Reverb scaling and cache/session must not share a Redis logical DB by accident). Flipping it is its own small change with its own verification.

**Decision 4 — Channel-naming discipline is enforced by test, not by hope.**
With zero real channels, the highest-leverage artifact is the exemption-aware registry test that will catch the FIRST module that forgets the tenant prefix. This is the real-time analogue of the multi-tenancy `withoutGlobalScopes` regression test: it makes the safe path the default and the unsafe path loud at build time.

## Risks
| Risk | Likelihood | Mitigation |
|------|------------|------------|
| A future module registers a channel without the `school_id` prefix, leaking cross-tenant broadcasts | High if uncontrolled | Shared name-builder helper; exemption-aware channel-registry discipline test that fails the build on any non-exempt channel lacking the tenant segment; documented convention |
| A module authorizes against request-scoped `TenantContext` inside a closure, breaking silently when the broadcast is queued | Med-High | Helper encodes `$user->school_id` comparison as the ONLY sanctioned predicate; convention explicitly forbids `TenantContext` in channel closures; documented rationale |
| Tenant-aware `api` limiter mis-keys landlord/unresolved requests (null `school_id`) and merges or over-splits buckets | Med | Null `school_id` falls back to the existing user/IP key (no landlord behavior change); behavioral partition test covers two-tenant independence and the null-tenant fallback |
| Enabling Reverb scaling later collides on a shared `REDIS_*` logical DB with cache/session | Med (deferred) | Documented as the flip-time verification; scaling stays off this change; explicit DB/instance separation required before enabling |
| Establishing the pattern with zero prior art (no real channels to test end-to-end) | Med | Guardrail test asserts discipline now; end-to-end subscribe/receive isolation deferred to first real feature with an explicit note; judgment-day recommended after design per repo policy |
| Reordering `ResolveTenant` before `throttle:api` (required for the tenant-aware limiter to see a bound tenant) puts an uncached DB query in front of every unthrottled request, letting bot/flood subdomain-scanning traffic hit the database unthrottled | Med-High | `ResolveTenant`'s School-by-subdomain lookup is cached (`tenant:school:{subdomain}`, 5-min TTL) using a non-null sentinel so BOTH positive (active tenant) and negative (nonexistent/inactive subdomain) lookups are cached — closing the gap for the scanning traffic that overwhelmingly targets nonexistent subdomains |
| Caching negative lookups introduces a staleness window where a deactivated School still resolves as active for up to the cache TTL, contradicting `ResolveTenant`'s "fail-closed" doc comment | Med | `SchoolCacheObserver` on `School`'s `saved`/`deleted` events invalidates the cache key (and the old key if `subdomain` changed) synchronously on every School change, so admin deactivation takes effect immediately instead of waiting out the TTL; `App\Tenancy\Models\School` carries `#[ObservedBy(SchoolCacheObserver::class)]` so the observer is actually wired to Eloquent's dispatch |
| School cache invalidation has a narrow transaction-commit race window (if School updates are wrapped in `DB::transaction()`, the `saved`-event `Cache::forget()` fires before commit) | Low (no production traffic yet, requires concurrent admin write + concurrent tenant request in the same ~ms window) | Accepted as documented foundation-stage risk; revisit with `DB::afterCommit()`-based invalidation if it becomes operationally relevant |
| Presence channels (future) leak member identity across tenants even with a scoped name | Low (out of scope) | Explicitly deferred; documented that presence member-list privacy needs its own decision when the first presence feature appears |

## Rollback Plan
No git in use and no real-time features or tenant broadcast data yet. Rollback = revert the `api` limiter closure in `app/Providers/AppServiceProvider.php` to its user/IP-only key, remove the `App\Tenancy\Broadcasting` helper, remove the guardrail test file(s), and revert any `routes/channels.php` convention comment. The `REVERB_SCALING_ENABLED=false` default is unchanged from today, so there is nothing to revert there. Engram artifacts remain. Because no module broadcasts yet, rollback is essentially free — which is exactly why doing this now is cheap.

## Dependencies
- **`multi-tenancy-foundation`** — REQUIRED and consumed: `School`, `TenantContext` (already app-`scoped` in `AppServiceProvider::register()`), `TenantScope`, `BelongsToTenant`, `ResolveTenant`, and `users.school_id`. This change adds no tenancy primitives; it applies them to the broadcast path.
- Existing installed stack only: Laravel 12, Laravel Reverb, Redis (all already provisioned). NO new Composer package.
- `routes/channels.php` and the auto-registered `/broadcasting/auth` route (confirmed present; single default channel today).

## Proposal question round (for user review before spec/design)
The architectural decisions above are resolved with the exploration-recommended answers. Flagging the assumptions that most change spec/design if wrong — confirm, correct, or request a second round:
1. **Channel name shape**: `private-school.{schoolId}.{resource}.{id}` with numeric `schools.id` as the tenant segment. Acceptable, or do you want an opaque/non-enumerable tenant token in the channel name (to avoid exposing the numeric school id to the client)? This is the single most design-shaping choice.
2. **Helper form**: a small `App\Tenancy\Broadcasting` helper (name builder + auth predicate) shared across modules. Confirm the tenancy-core placement, or do you prefer a per-module convention with only a documented rule and no shared code?
3. **`api` limiter key composition**: partition per `school_id` while keeping the existing user/IP sub-key (`school:{id}|{user-or-ip}`). Confirm, or should the tenant become the SOLE key (coarser, one bucket per school regardless of user)?
4. **Reverb scaling stays off** this change, flipped later as its own change once real concurrent-connection load is measured. Confirm the defer, or is multi-instance Reverb expected soon enough to include enabling + verifying it here?
5. **Guardrail scope**: build the exemption-aware channel-registry discipline test now (passes trivially today, guards the future) and defer end-to-end subscribe/receive isolation to the first real feature. Confirm, or do you want a throwaway sample channel created solely to prove end-to-end isolation now?
6. **Frontend/Echo wiring stays out of scope** (backend authorization/isolation only). Confirm, or should client-side Echo subscription conventions be documented in this same change?
