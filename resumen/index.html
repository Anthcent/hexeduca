Cómo está armado el sistema

Glosario en simple

Antes de entrar en diagramas técnicos, esto es lo que significa cada término que vas a ver repetido en toda la página.

Monolito modular

Es una sola aplicación (un solo proceso, un solo deploy) pero organizada en carpetas separadas por tema ("módulos"). No son microservicios: si un módulo se cae, se cae toda la app, porque comparten el mismo proceso PHP.

Arquitectura hexagonal

Divide cada módulo en 3 capas: Domain (las reglas de negocio puras, sin Laravel), Application (los "casos de uso", qué pasos ejecutar), Infrastructure (cómo se conecta con la base de datos, HTTP, etc). La idea es poder cambiar Infrastructure sin tocar las reglas de negocio.

Multi-tenancy (tenant)

Un mismo sistema atiende a varias escuelas ("tenants") con los mismos datos guardados juntos en la misma base, pero filtrados: cada escuela solo ve lo suyo. Se identifica por subdominio (colegioX.app.com).

Evento de dominio

Un "aviso" que un módulo lanza cuando pasó algo importante (ej: "se creó una oferta académica"). Otros módulos pueden escuchar ese aviso y reaccionar (mandar un email, generar una notificación) sin que el módulo original sepa quién escucha.

Middleware

Un filtro que se ejecuta antes de que la request llegue al controller: valida sesión, tenant, rol, límites de velocidad, etc. Si el middleware rechaza, el controller nunca se entera de que hubo un pedido.

RBAC (Role-Based Access Control)

Control de permisos por rol (student, teacher, staff/admin, super-admin) en vez de por usuario individual. Hoy solo controla "qué rol puede entrar a qué ruta", todavía no controla acciones finas dentro de una pantalla.

Síncrono vs. en cola (queue)

Síncrono = pasa dentro del mismo request, el usuario espera a que termine todo. En cola = se guarda el trabajo para un proceso aparte ("worker") que lo hace después, en background — si falla, no le rompe la pantalla al usuario.

Rate limiting (throttle)

Un límite de cuántas veces se puede llamar a una ruta en un minuto, para evitar que alguien (a propósito o por error) sature el servidor con pedidos repetidos.

Módulos (Modules/*)

Cada módulo sigue el patrón Domain → Application → Infrastructure. El dominio es PHP puro (sin Eloquent); la infraestructura implementa los repositorios e integra con Laravel.

Cómo leer este diagrama
Domain — PHP puro, cero dependencias de Laravel/Eloquent. Define entidades, interfaces de repositorio y eventos. Es lo que sobreviviría si mañana cambian de framework.
Application — los UseCases orquestan: reciben datos, llaman al Domain, deciden qué evento disparar. No saben cómo se guardan los datos, solo el "qué hacer".
Infrastructure — la parte "sucia": Eloquent Models, implementaciones concretas de los repositorios, Controllers HTTP, y el ServiceProvider que conecta interfaz → implementación.
Flechas sólidas (→) — dependencia directa de código (import real).
Flechas punteadas (-.→) — relación indirecta: implementa una interfaz o se registra en tiempo de boot, no es un import directo.

Cómo leer este diagrama
Rombos ({ }) — son decisiones (if/else); cada rama sale hacia un resultado distinto.
Host landlord — el dominio "administrador" (ej. admin.app.com) que NO pertenece a ninguna escuela — ahí los filtros de tenant se desactivan.

Global scope Eloquent: filtra por school_id del TenantContext. No-op si no hay tenant.

TenantChannel

Broadcasting (Reverb) aislado: school.{id}.{recurso}.{id}. Autoriza contra user.school_id (no hay request scope en el proceso de Reverb).

SchoolCacheObserver

Invalida la cache de 5min al guardar/borrar una School. ⚠ No usa DB::afterCommit().

Fallos en cascada: monolito síncrono sin aislamiento

Análisis del escenario: ¿qué pasa si un módulo falla en medio de un request? Verificado en código, no es hipotético — es consecuencia directa de que no hay listeners registrados ni cola async.

Cómo leer este diagrama
Parte de arriba (sin alt) — lo que pasa HOY de verdad: el evento se dispara pero muere en el vacío, nadie lo escucha, nada se rompe.
Bloque alt — es un escenario HIPOTÉTICO/futuro, no código actual: "si mañana alguien agrega un listener síncrono de la forma obvia, esto es lo que pasaría".
L--x L (excepción) — el símbolo --x marca una falla; la excepción no se queda contenida en el listener, sube (bubble up) por el mismo stack de llamadas de PHP.
UC-->>C: excepción sube — flecha punteada de vuelta: es el camino de vuelta del error, no una llamada nueva — mismo hilo de ejecución, mismo request.
Nota final — el punto clave del riesgo: la escritura en base de datos ya es un hecho consumado antes de que el listener falle, pero el usuario ve un error como si nada se hubiera guardado.

Riesgo real detectado

Como no hay cola (ShouldQueue no está en uso en ningún listener porque no hay listeners), el día que se implemente Modules/Notifications de la forma "obvia" — un Listener::handle() síncrono escuchando EstudianteMatriculado — cualquier falla ahí (SMTP caído, excepción de código, timeout de un servicio externo) sube por el mismo stack de PHP y tumba el request completo del módulo que disparó el evento. Academic no se "cae" por su propio código — se cae porque Notifications, ejecutando en el mismo proceso sin aislamiento, no le devolvió el control.

Efecto secundario: escritura ya confirmada

El INSERT de la matrícula ya pasó y (si no hay DB::transaction() envolviendo UseCase + evento) puede estar comprometido antes de que el listener falle. El usuario recibe un 500, no sabe si su matrícula quedó guardada, y probablemente reintenta — con riesgo de duplicado si no hay constraint único cubriendo ese caso (acá sí hay unique(oferta+student) en MATRICULAS, así que el duplicado exacto fallaría, pero el usuario igual ve un error que no refleja la realidad: la operación de negocio principal sí se completó).

Por qué pasa: acoplamiento por ejecución, no solo por código

Aunque el patrón de eventos parece desacoplado (Academic no importa clases de Notifications), en la práctica el acoplamiento existe a nivel de ejecución: mismo proceso, mismo hilo, misma transacción de request. Un evento síncrono no es distinto de una llamada directa en términos de blast radius — solo cambia la sintaxis, no el aislamiento de fallos.

Mitigación disponible sin reescribir arquitectura

Laravel ya tiene la pieza para esto: ShouldQueue en el listener. Con eso, el evento se despacha a un job, el request principal termina y responde 200 sin esperar al listener, y si el listener falla, falla en el worker — con reintentos y failed_jobs para inspección, sin tumbar el flujo del usuario. Esto no está implementado todavía porque Notifications sigue siendo esqueleto — queda anotado como requisito de diseño para cuando se implemente, no como bug actual.

Cómo funciona hoy la infraestructura de colas (ya existe, no se usa)

Verificado en config/queue.php y app/Support/SecurityPolicy.php — el proyecto ya tiene todo lo necesario para aplicar la mitigación, no hace falta infraestructura nueva.

jobs table — no es un servicio nuevo: es una tabla más dentro de la misma Postgres del proyecto (driver database), donde se guarda "pendiente: ejecutar este listener".
Worker (queue:work) — un proceso PHP aparte, de larga duración, que va tomando jobs de esa tabla y ejecutándolos uno por uno — no es el mismo proceso que responde requests HTTP.
L--x L (falla) dentro del worker — acá una falla del listener NO afecta al usuario en absoluto, porque el usuario ya recibió su respuesta antes de que el worker siquiera empiece a procesar el job.
Nota final — es el punto central de la mitigación: se rompe la dependencia temporal entre "la matrícula se guardó" y "la notificación se mandó".

Driver activo: database

config/queue.php:16 → QUEUE_CONNECTION default es database, no Redis/SQS. Usa la tabla jobs de la misma Postgres — cero infraestructura nueva para arrancar. Se puede migrar a Redis después si el volumen lo justifica, sin cambiar el código de los listeners.

⚠ Gotcha real: after_commit = false

config/queue.php:43 tiene 'after_commit' => false para el driver database. Esto significa que si el evento se dispara dentro de un DB::transaction() que todavía no hizo commit, el job puede encolarse y el worker puede intentar leer datos que aún no están confirmados. Hay que fijar after_commit a true (global o por job con $job->afterCommit()) antes de implementar Notifications — mismo patrón de bug que ya está anotado para SchoolCacheObserver.

Reintentos y falla definitiva

retry_after => 90s ya configurado. Falta definir en cada listener: public $tries, backoff(), y un método failed() — hoy no hay ningún listener, así que no hay ninguno de estos definidos todavía.

Operación: falta el worker corriendo

El driver database no procesa nada solo — requiere php artisan queue:work corriendo como proceso persistente (systemd/Supervisor en prod, o sail artisan queue:work en local). Esto no está documentado en el proyecto todavía; queda como tarea de despliegue cuando se implemente el primer listener real.

Una sola cadena de dependencia vertical

Tenant (escuela) resuelve primero. Periodo académico activo depende del tenant y rige el resto del contexto de negocio (qué año, qué sección, qué momento — mañana/tarde/noche). Ningún módulo de negocio debería estar arriba ni en el medio de esa cadena.

Módulos como hermanos, no como capas

Academic, Users, Files, Grades, Notifications, Schedule reciben el mismo contexto (tenant + periodo) pero ninguno se construye "encima" de otro. Si Grades necesita saber algo de Academic, lo pide vía evento/contrato — nunca importando un modelo o UseCase de Academic directamente.

Datos variables no son una estructura fija

Año, sección, momento (mañana/tarde/noche) pueden variar por escuela y por periodo — no son un catálogo universal que un módulo pueda asumir "hardcodeado". Cada módulo los consulta a través del contrato del periodo activo, no leyendo directamente la tabla de otro módulo.

Criterio de éxito: agregar un módulo no toca los demás

Implementar un módulo nuevo (o terminar uno esqueleto) debería significar: registrar sus rutas + suscribirse a los eventos que le interesan. Cero cambios en el código de Academic, Users o cualquier otro módulo ya existente para que el nuevo funcione.

Deuda técnica y puntos a seguir

Cosas verificadas en el código, no supuestos.

Eventos de dominio sin listeners

OfertaAcademicaCreated, EstudianteMatriculado, UserRegistered se disparan (o ni eso) sin que nada los escuche. Notifications está vacío.

RegisterUser UseCase muerto

AuthController::register no pasa por el UseCase del Domain — crea el User directo con Eloquent, rompiendo la arquitectura hexagonal declarada para ese flujo.

RBAC sin permisos finos

4 roles globales sembrados, pero sin ningún permission asignado — la matriz de permisos está explícitamente fuera de alcance del cambio actual (openspec/changes/auth-rbac).

Cache de tenant sin afterCommit

SchoolCacheObserver invalida la cache de 5min antes de que un DB::transaction() externo haga commit — riesgo de servir datos viejos ante escrituras concurrentes.

4 módulos sin ninguna protección de ruta

Files, Grades, Notifications y Schedule registran rutas resource sin auth — hoy no importa porque los controllers son stubs, pero es una trampa para cuando se implementen sin agregar middleware a mano.

Riesgo de diseño: listeners futuros sin ShouldQueue tumbarían el módulo que dispara el evento

Ver detalle en Fallos en cascada. Como los eventos hoy no tienen listeners, no es un bug activo — pero si Notifications se implementa con un listener síncrono "obvio", cualquier falla ahí (SMTP, timeout) tumba el request completo de Academic/Users que disparó el evento, porque todo corre en el mismo proceso PHP sin cola. Requisito de diseño a aplicar antes de implementar Notifications: todo listener debe implementar ShouldQueue.

Rutas web sin rate limit

Los throttles configurados (app/Providers/AppServiceProvider.php) solo cubren login (5/min, SecurityPolicy::LOGIN_ATTEMPTS_PER_MINUTE) y el grupo api (60/min, ya keyed por tenant tras realtime-tenant-isolation). Las rutas web normales — crear oferta, matricular, etc. — no tienen throttle explícito en bootstrap/app.php. Propuesta consistente con el patrón ya existente: agregar un tercer limiter RateLimiter::for('web', ...) en el mismo AppServiceProvider::boot(), keyed igual que api (user_id|school_id o IP si es guest) y aplicarlo al grupo web en bootstrap/app.php, con un límite más generoso (ej. 120/min) para no afectar navegación normal.
