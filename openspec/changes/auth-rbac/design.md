# Design: Auth + Role Assignment (auth-rbac)

## Technical Approach
Thin Inertia controllers over Laravel's native `Auth` and Spatie's `assignRole`/`syncRoles` — no new domain entities, mirroring `academic-offering-management-ui`. One `AuthController` (login/register/logout) plus `edit`/`update` on the existing `UsersController`. Three FormRequests hold validation. A `UserPolicy` centralizes the tenant-ownership and super-admin-escalation authorization. `HandleInertiaRequests::share()` gains a lazy `auth.user` prop. Spatie middleware aliases already exist in `bootstrap/app.php` (verified) — no change there.

The load-bearing constraint: `ResolveTenant` (on the `web` group) resolves the tenant **only from the request host** and is **fail-closed** — a tenant subdomain binds that tenant, the bare base domain and unknown subdomains `abort(404)`, and only configured landlord hosts (`admin.app.com`) pass with **no** tenant bound. The proposal's public school `<select>` is therefore coherent **only on the landlord host**, where no tenant is pre-bound and `User` queries are unscoped.

## Architecture Decisions

### Decision: Only registration is route-constrained to the landlord host, enforced by middleware (not `Route::domain()`)
**Choice**: `/login`, `/logout`, `users.edit`, `users.update` are ordinary routes in `Modules/Users/routes/web.php`, reachable on whatever host `ResolveTenant` resolves — normally a school's own subdomain (e.g. `schoolA.app.com/login`). Only `GET/POST /register` is gated to the landlord host, and the mechanism is a dedicated middleware, `RequireLandlordHost`, applied to the `register` route group — **not** `Route::domain()`. The middleware compares `strtolower($request->getHost())` against `array_map('strtolower', (array) config('tenancy.landlord_hosts', []))` — the exact same config array and normalization `ResolveTenant` already applies — and `abort(404)` on mismatch. Registration explicitly sets `school_id` from the form select.
**Alternatives**: `Route::domain($host)->group(...)` looped once per entry in `config('tenancy.landlord_hosts')` (rejected — with multiple comma-separated landlord hosts this registers the same route name, e.g. `register`, multiple times; Laravel keeps only the last-registered match, so `route('register')` and any redirect built from it resolve to the wrong host for every landlord host except the last one); gating `/login`/`/logout`/`users.edit`/`users.update` to the landlord host too, as an earlier design draft did (rejected by explicit product decision — login must work per school subdomain, e.g. `schoolA.app.com/login`, not centralized on a single landlord host; only registration caused the actual cross-tenant bypass, because it is the one flow where an unauthenticated visitor explicitly picks which school to join via the public school `<select>`); leaving `/register` host-agnostic and relying on `BelongsToTenant`'s `creating` hook alone (rejected — the hook only auto-stamps `school_id` when null, so an explicit non-null `school_id` submitted from a tenant subdomain always wins, letting a visitor on `schoolA.app.com/register` self-register directly into `schoolB` and defeating subdomain-based tenant isolation; this is normal form submission, not an attack, so it cannot be treated as an edge case).
**Rationale**: On the landlord host `TenantContext` is empty, so `School::withoutTenantScope()->where('is_active',true)` can list all schools for the registration picker, and `BelongsToTenant`'s `creating` hook auto-stamps nothing — the controller's explicit `school_id` wins (`school_id !== null` short-circuits the hook). A host constraint is required for `/register` specifically, not just a convention: without it, `/register` is reachable on any tenant subdomain, where the explicit `school_id` still wins over the (no-op) auto-stamp and a visitor can register into a school different from the one implied by the subdomain they're on. A middleware check (rather than `Route::domain()`) closes this without duplicating the `register` route registration: there is only ever one `register` route, so there is no named-route collision to worry about, and reusing the identical `strtolower(...)`/`array_map('strtolower', ...)` normalization `ResolveTenant.php` already uses means a non-lowercase-configured landlord host is recognized identically at both layers — no silent 404 from a casing mismatch. This one-line normalization is duplicated between `ResolveTenant` and `RequireLandlordHost` rather than extracted into a shared helper/trait; both are one-liners reading the same config key, and a shared abstraction would add an indirection layer without meaningfully reducing risk — acceptable duplication given the size.
`Login/logout routes are deliberately NOT host-gated by middleware`: a user submitting `POST /login` on `schoolA.app.com` has `ResolveTenant` bind the `schoolA` tenant before the controller runs, so `Auth::attempt`'s underlying `User::where('email', ...)` lookup is naturally scoped by `TenantScope` to `schoolA` — no cross-tenant leak, and no landlord-host detour is needed for an ordinary user to log into their own school. This also removes any dependency on `SESSION_DOMAIN` for the login/logout flow on a tenant subdomain: a user who logs in on their own subdomain never needs their session recognized on a different host to keep using that subdomain. However, `/login` **is** reachable on the landlord host (no middleware blocks it there), and on that host `ResolveTenant` binds no tenant at all, so `TenantScope` no-ops and the `Auth::attempt` lookup is globally unscoped across every school. This is not an oversight: it is the only viable login path for the landlord super-admin (`school_id = null`), since `TenantScope` would exclude that row on every real tenant subdomain. Left unrestricted, though, it would also let any ordinary user authenticate on the landlord host with an unscoped lookup. See "Decision: Landlord-host login restricted to super-admin" below for the role-check that closes this without host-gating the route itself.

### Decision: super-admin escalation guarded by a UserPolicy (not inline, not Gate closure)
**Choice**: `UserPolicy::assignRole(User $actor, User $target, string $role): bool`:
```php
if ($actor->hasRole('super-admin')) return true;           // landlord: any tenant, any role
return $actor->school_id !== null
    && $actor->school_id === $target->school_id            // same-tenant only
    && $role !== 'super-admin';                            // staff/admin cannot grant super-admin
```
Registered via `Gate::policy(User::class, UserPolicy::class)` in `UsersServiceProvider::boot()` — mandatory because the model lives outside `App\Models`, so Laravel 11 auto-discovery will NOT find it.
**Alternatives**: inline `if` in controller (scatters authz, not unit-testable, easy to forget on re-check); `Gate::define` closure (no gate-definition convention exists in the module; a Policy class is more discoverable and model-bound).
**Rationale**: The rule depends on the actor role, the target's tenant, AND the submitted role value — a Policy method accepting extra args (`$this->authorize('assignRole', [$user, $role])`) models all three, throws 403 automatically, and is independently testable. `users.edit`/`users.update` are per-tenant/subdomain routes (no landlord-host constraint — an admin authenticated on their own school's subdomain per the decision above already holds a tenant-scoped session when reaching this screen), so `User::findOrFail($id)` is naturally scoped by `TenantScope` to the admin's own tenant, but only when a tenant is actually bound. `TenantScope` provides tenant-filtering ONLY when a tenant is bound to the request (i.e., on a real tenant subdomain); it is not something `UserPolicy::assignRole` can rely on being present on every host. `UserPolicy::assignRole`'s manual `$actor->school_id === $target->school_id` comparison is therefore the enforcement mechanism that always applies, on any host, bound or not — it is what guarantees correctness even where `TenantScope` cannot help (an unbound host) — with `TenantScope` acting only as an additional narrowing filter on tenant subdomains where it is applicable. Do not read this as "second independent layer, not sole enforcement": `TenantScope` is not a guaranteed second check in all cases, so `UserPolicy::assignRole` cannot be described as merely one of two equally-reliable layers.

### Decision: Landlord-host login restricted to super-admin
**Choice**: `/login` remains an ordinary, host-unconstrained route (see the decision above — no `RequireLandlordHost` middleware on it). Instead, `AuthController::login` performs an explicit landlord-host check immediately after `Auth::attempt` succeeds: if `in_array(strtolower($request->getHost()), array_map('strtolower', (array) config('tenancy.landlord_hosts', [])), true)` is `true` (the exact same normalization `ResolveTenant`/`RequireLandlordHost` already use) and the freshly authenticated user does NOT have the `super-admin` role (`$request->user()->hasRole('super-admin')`, matching the exact role string seeded by `SuperAdminUserSeeder`), the controller immediately logs the user back out (`Auth::logout()`, invalidate session, regenerate CSRF token) and returns the same generic "invalid credentials" validation error used for a bad password (`ValidationException` on the `email` field) — it does NOT return a distinct message revealing that the account exists but is barred from this host.
**Alternatives**: Gating `/login` behind `RequireLandlordHost` the way `/register` is gated (rejected — that would block the landlord super-admin's only working login path entirely, since `TenantScope` excludes `school_id = null` on every real tenant subdomain); checking the role before calling `Auth::attempt` via a pre-lookup (rejected — would require an unscoped `User::where('email', ...)` lookup ahead of `Auth::attempt`, duplicating the query and creating a second globally-unscoped code path; simpler and no less safe to let `Auth::attempt` run first, since it is already globally unscoped on this host by construction, and immediately reject afterward); returning a distinct "not authorized on this host" error (rejected — leaks account existence/host-eligibility to an attacker, i.e. user enumeration).
**Rationale**: On the landlord host, `ResolveTenant` binds no tenant, so `TenantScope` no-ops and `Auth::attempt`'s lookup is globally unscoped across every school — this is required for the landlord super-admin to be able to log in at all (their `school_id` is `null` and never matches a bound tenant elsewhere), but it would otherwise let ANY user, of any school, authenticate via the landlord host with an unscoped session. The role check closes that gap without touching the route's reachability: ordinary users can still fail to authenticate on the landlord host (rejected, generic error, no enumeration), while the super-admin's login continues to work exactly as today. On a real tenant subdomain, no equivalent check is needed: `TenantScope` already naturally excludes `school_id = null` (the super-admin) from any subdomain's scoped `User::where('email', ...)` lookup, so `Auth::attempt` already fails there for that account without any new code — this is already-sufficient and deliberately not duplicated.

### Decision: Registration does not establish a session on the landlord host
**Choice**: `AuthController::register` creates the `User` and assigns `student`, then redirects to `School::loginUrl()` (a small new helper on the `School` model that concatenates `$this->subdomain` with `config('tenancy.base_domain')`, scheme derived from `request()->getScheme()` rather than hardcoded — the same convention `ResolveTenant::subdomainLabel()` already relies on in reverse) with a `?registered=1` query parameter. It does NOT call `Auth::login($user)` and does NOT regenerate the session. The visitor authenticates for the first time through the ordinary `POST /login` flow on their own school's subdomain, where `Login.vue` reads `registered=1` from the query string to render its own static "Account created — log in below" copy.
**Alternatives**: `Auth::login($user)` immediately after `assignRole('student')`, redirecting home (rejected — this is the CRITICAL gap identified in round-4 review: `/register` is landlord-host-only, and on the landlord host `TenantScope` no-ops, so an `Auth::login()` call there leaves a non-super-admin authenticated with a live, globally-unscoped session on exactly the host the "Landlord-host login restricted to super-admin" decision was built to lock down — reachable via the registration entry point instead of `/login`); auto-login followed by an immediate forced logout-and-redirect (rejected — strictly more complex than never authenticating in the first place, and briefly creates the same unscoped session it then has to tear down); a session `with('success', ...)` flash message (rejected — round-5 review: the flash would be written to the landlord-host session cookie, which a browser never sends to the different tenant-subdomain host it's redirected to, so the message would silently never render; a query parameter carries the signal host-agnostically with no cookie dependency).
**Rationale**: This keeps registration and login consistent with the same invariant: only a `super-admin` may ever hold an authenticated session on the landlord host. A freshly-registered `student`/`teacher`/`staff/admin` account never touches that host with an active session at all, so there is no window, however brief, where an unscoped `TenantScope` session exists for a non-super-admin. The visitor is redirected straight to the tenant subdomain implied by the `school_id` they picked, where `POST /login` naturally scopes the subsequent `Auth::attempt` lookup to that school, and the `?registered=1` query flag survives the cross-host redirect since it isn't tied to either host's session cookie.

### Decision: single role name in share(), recomputed per request
**Choice**: `'role' => $request->user()->getRoleNames()->first()` inside a lazy closure; no permission arrays.
**Rationale**: Matches proposal. `syncRoles` clears the loaded relation on write, so the next request reflects the new role despite Spatie's 24h cache (`events_enabled=false`).

## Data Flow
Only `GET/POST /register` is gated to the landlord host, via the `RequireLandlordHost` middleware (see "Only registration is route-constrained to the landlord host, enforced by middleware" above). `/login`, `/logout`, `users.edit`, and `users.update` are per-tenant routes reached on whatever host `ResolveTenant` resolves (typically a school's own subdomain) and carry no host constraint of their own.
```
GET /register (landlord host only, no tenant) -> AuthController::showRegister
   schools = School::withoutTenantScope()->where('is_active',true)->get(['id','name'])
   -> Inertia 'Users::Register' {schools}
POST /register (RegisterRequest) (landlord host only) -> User::create(name,email,password,school_id) explicit
   -> assignRole('student') -> redirect to School::loginUrl() . '?registered=1' (tenant subdomain, e.g. https://{school->subdomain}.{tenancy.base_domain}/login?registered=1)
   // No Auth::login(), no session regenerate: the landlord host never receives
   // an authenticated session for this account. First authentication happens
   // via the normal per-tenant POST /login flow, already scoped by TenantScope.
   // The ?registered=1 query flag (not a session flash) survives the cross-host
   // redirect; Login.vue reads it to show a static "account created" message.
POST /login (LoginRequest, throttle:login) (host-unconstrained: reachable on a tenant subdomain, e.g. schoolA.app.com/login, AND on the landlord host) -> Auth::attempt(email,password)
   // TenantContext is bound by ResolveTenant only on a tenant subdomain, so the
   // underlying User::where('email', ...) lookup is naturally scoped there;
   // on the landlord host no tenant is bound and the lookup is globally unscoped
   fail -> back withErrors('email')
   ok on tenant subdomain -> session regenerate -> redirect intended
   ok on landlord host -> if authenticated user lacks role 'super-admin':
      Auth::logout() + session invalidate + regenerateToken -> back withErrors('email') (same generic message, no enumeration)
   ok on landlord host, user has role 'super-admin' -> session regenerate -> redirect intended
POST /logout (host-unconstrained) -> Auth::logout + session invalidate + regenerateToken -> redirect login

GET /users/{id}/edit  [auth, role:staff/admin|super-admin] (per-tenant subdomain)
   User::findOrFail($id)   // TenantScope scopes this to the admin's own tenant only when
                           // a tenant is bound (i.e. on their subdomain); UserPolicy::assignRole's
                           // school_id comparison below is what always applies, on any host
   authorize('assignRole', [$user, $user->getRoleNames()->first()])
   -> Inertia 'Users::Edit' {user:{id,name,email,role}, roles:[4 fixed]}
PUT /users/{id} (UpdateUserRoleRequest) (per-tenant subdomain)
   -> findOrFail   // TenantScope-filtered query
   -> authorize('assignRole',[$user,$role])
   -> $user->syncRoles([$role]) -> back with('success')
```

## Interfaces / Contracts
`unique:users,email` and `exists:schools,id` use the query builder — they bypass Eloquent global scopes, so email is enforced **globally unique** (consistent with unscoped landlord-host login). Vue pages read `form.errors.<field>` mapped to FormRequest keys; `auth.user` prop is `{id,name,email,role}` or `null`.

## Migration / Rollout
No schema changes; additive. Rollback: restore the `/login` closure, delete `AuthController`, Policy, FormRequests, Vue pages, revert `edit`/`update`, `share()`, and the module routes.

## Open Questions
Resolved for this change: only `GET/POST /register` is route-constrained to the landlord host, via the `RequireLandlordHost` middleware (see "Only registration is route-constrained to the landlord host, enforced by middleware"), not via `Route::domain()`. This closes the cross-tenant registration bypass directly — `/register` is unreachable from a tenant subdomain, so a visitor there cannot submit the school `<select>` to self-register into a different school. `/login` and `/logout` remain host-unconstrained routes, but `/login` gains an explicit in-controller role check for the landlord host (see "Decision: Landlord-host login restricted to super-admin"): on the landlord host, only the seeded `super-admin` may complete authentication — any other user who successfully passes `Auth::attempt` there is immediately logged back out and rejected with a generic error. `users.edit` and `users.update` remain per-tenant/subdomain routes: they run wherever `ResolveTenant` binds a tenant (normally the user's own school subdomain), with `TenantScope` scoping the relevant queries only when a tenant is bound, and `UserPolicy::assignRole`'s `school_id` comparison providing the enforcement that always applies regardless of host.

`SESSION_DOMAIN` is no longer a dependency of this change at all: no route added or modified by auth-rbac requires a cross-host session handoff. Login/logout on a tenant subdomain happen directly on the host the session is used on; the super-admin's login on the landlord host likewise establishes a session used only on that same landlord host; and registration on the landlord host establishes no session at all — the post-registration redirect sends the visitor straight to their own school's subdomain `/login` page, per "Decision: Registration does not establish a session on the landlord host". Any future work that would move an authenticated user from the landlord host onto a tenant subdomain post-login remains a genuine, separate follow-up, but it is not triggered by anything in this change.

Remaining out of scope for this change:
- [ ] None currently open for the auth/route-host-scoping topic addressed above; other unresolved suspects from prior review rounds (e.g. the `assignRole` GET-reuse suggestion, the post-registration redirect target, and possible actor-role checks in `UserPolicy`) are tracked separately and untouched by this fix.
